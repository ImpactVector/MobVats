MobVats Slice 11.0.1 - standard process-fluid buckets

Registrations
  Source fluid                    Filled bucket item
  mobvats:meat                     mobvats:meat_bucket
  mobvats:waste                    mobvats:waste_bucket
  mobvats:culture_slurry           mobvats:culture_slurry_bucket
  mobvats:feeding_slurry           mobvats:feeding_slurry_bucket
  mobvats:experience               mobvats:experience_bucket

All use vanilla BucketItem, stack size 1, and the empty vanilla bucket as
crafting remainder. NeoForge supplies the standard fluid-item capability
through FluidBucketWrapper. Each filled bucket represents exactly 1000 mB.
Both source and flowing BaseFlowingFluid properties reference the bucket.
FluidUtil.tryEmptyContainer / tryFillContainer work with a generic FluidTank.
These helpers return a replacement ItemStack; callers must retain that result.

Presentation
The five buckets are appended after the syringe in the MobVats creative tab.
Each has an English name and a neoforge:fluid_container model inheriting
neoforge:item/bucket. NeoForge's standard fluid item color handler uses the
existing fluid colors and water textures. No custom artwork is required.

Minimum world placement
Generic container transfer itself does not need liquid blocks. However, the
standard BucketItem in-world use path directly places the fluid's legacy block.
Without a registered block, BaseFlowingFluid returns air, which can produce
failed placement or remove a replaceable block without preserving the fluid.
To keep ordinary BucketItem use correct without custom container/use code,
each fluid has a minimal LiquidBlock registered under its source name in the
block registry (e.g. block mobvats:meat). These blocks have no BlockItems.
Their properties copy vanilla water; the existing fluid properties are retained.

In-world use at an eligible location places one matching source block and
returns an empty bucket under normal survival BucketItem semantics. The liquid
can flow using BaseFlowingFluid defaults and existing tinted water rendering.
An empty vanilla bucket picks up a source into the matching filled bucket;
flowing liquid is not a collectible source. Source conversion remains disabled.
There are no custom source-generation rules, reactions, or special interactions.

Compatibility and scope
Existing source/flowing fluid IDs, fluid types, density, viscosity, process
selectors, recipes, configuration IDs, and saved fluid identities are unchanged.
Only bucket item and liquid block registrations are added; no migration is
required. There is no Buffer/Port/Drain bucket interaction, service staging,
filter interaction, routing change, Void block, GUI, or productivity change.

  .\gradlew.bat runGameTestServer    PASS: all 252 required tests
  git diff --check                  PASS

ProductFluidGameTests adds six tests: one full bucket contract for each fluid
and one process-selector/Mixer-output regression test. Each fluid contract
checks source/flowing/bucket registration, empty bucket remainder, stack size,
the standard capability, ItemStack save/load, exactly 1000 mB generic transfer
and refill, simulated transfers without source mutation, rejection of partial
transfers and undersized tanks, rejection of all four other MobVats fluids,
no repeated drain/refill duplication, and source placement/pickup identity.
The complete run includes existing Vat, Mixer, Fluid Buffer, and physical
storage regressions. GameTest code remains excluded from the distributable.
