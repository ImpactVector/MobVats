MobVats Slice 11.1 - Fluid Buffer interactions and exact port filters

Interactions
  Fluid Buffer: normal right-click with a NeoForge fluid-capability container.
  Filled containers insert; empty containers extract. Vanilla buckets transfer
  1000 mB atomically. Other containers retain their standard capability transfer
  policy, including partial transfers. Container replacement, stacked-container
  inventory stowing, sounds, and creative-mode behavior use FluidUtil helpers.
  Rejected container clicks are consumed so a bucket cannot place liquid instead.

  An empty logical cluster adopts/resets an exact fluid ID after a successful
  insertion. A nonempty logical cluster refuses a different fluid/components.
  Draining preserves its filter. An empty fluid-capability container used on an
  empty filtered cluster clears all member filters without changing the container
  or creating fluid. This does not require that fluid to have a filled bucket.

  Item/Fluid Port: sneak-right-click with the item/filled container to sample;
  sneak-right-click with an empty hand to clear. Sampling copies/inspects the held
  stack and never consumes or mutates it. Formed-machine edits/clears are blocked
  with action-bar feedback. Ordinary port clicks retain their existing menu.
  The existing menu direction control remains unchanged.

Selectors and routing
  Exact item IDs use the existing ResourceSelectors identity policy: components
  such as custom names are ignored. Exact fluid filters use registered fluid IDs;
  actual stored FluidStacks retain their components and reject incompatible mixes.
  No tag configuration UI is exposed. Existing command-configured tag selectors
  continue loading. Filters constrain external capabilities, staging insertion,
  Tool result exports, planned item outputs, and internal item-input selection.
  Filtered Fluid Output tank inspection also hides excluded fluid contents.
  Conduits remain unchanged resource-only connectivity.

Persistence and migration
  Item CUSTOM_DATA contains mobvats_endpoint, version=1, filter=<selector>.
  Buffers additionally carry tank using FluidTank.writeToNBT (FluidStack codec:
  tank.Fluid.id/amount/components). Ports additionally carry output=<boolean>.
  Loot drops and pick-block capture only this physical/configuration state.
  Placement restores it through the shared EndpointState helper.
  Controller ownership, migration escrow, and port staging are excluded.
  Existing Item Port staging drops separately under the existing removal behavior.

  World-save formats are retained: Buffer filter/tank, Fluid Port fluidFilter,
  and the existing ZeroCore payload. Item Ports add itemFilter; absent means
  unfiltered. No destructive migration or escrow change is required. Unknown
  future portable-state versions are not applied by the version-1 placement path.

  Face-adjacent clustering retains the existing equal-filter and compatible-fluid
  rules. Members are sorted by the existing position comparator before compilation
  and distribution. Physical member tanks remain the only persisted ownership.
  Break/drop captures just the removed member's actual amount; merge/split cannot
  duplicate a logical shared tank. Unformed interactions compile the addressed
  adjacent cluster directly; configuration changes notify existing controllers.

Presentation
  Configured Buffer items use the localized fluid display name plus Buffer.
  Buffer tooltips show filter ID and exact amount / 4000 mB per physical block.
  Port tooltips show filter ID and Input/Output direction. Ports retain their
  established item names. Successful edits/transfers use concise action-bar text.

Autonomous coverage
  Slice111GameTests adds 16 tests covering bucket and non-bucket transfers,
  insufficient amounts/capacity, creative and stacked container semantics,
  filter retention/clearing/retargeting, real destruction and drop/place/pick
  persistence, physical cluster conservation and compatibility, item component
  policy, port sampling without consumption, formed locks and disassembly,
  filtered capabilities/output visibility/Tool exports, and old save loading.
  TestFluidContainer is a development-only 1500 mB capability fixture; all
  GameTest classes and its registration are excluded from the distributable.
  The existing buffered harvest-metrics fixture now explicitly blocks exports
  rather than depending on its assertion preceding the next routing cadence.

  git diff --check                  PASS
