MobVats Slice 11.2 - Endpoint service staging and formed Fluid Port containers

Architecture and ownership
  ServiceStaging is a shared endpoint component with independent 1000 mB tanks
  keyed and ordered by canonical fluid registry ID. It is serialized in the
  producing block entity's existing ZeroCore payload as serviceStaging. The
  controller's PhysicalFluidStorage holds routing references, not fluid copies.

  Specimen-owned Drains retain Waste, Experience, milk, and configured resource
  process fluids. Milk-producing cow, goat, and mooshroom definitions share this
  path. Milk uses the specimen's Drain as its physical fluid service origin,
  preserving existing topology and immediate Tool container output behavior.
  Blenders retain Meat locally, independently of Sword item output. Mixer
  Controllers retain Culture Slurry and Feeding Slurry independently. Other
  completed data-defined fluid/XP transforms use the same Drain abstraction.

  Producers prefer compatible physical bulk capacity; their own stage supplies
  the bounded fallback. They cannot put newly completed output into another
  producer's service reservoir. Full service/bulk output retains normal pending
  process work and backpressure. No fluid is voided. Batches must fit available
  capacity according to the existing process transaction rules; staging does
  not raise the capacity of a Fluid Buffer or introduce a controller fluid pool.

Routing and interaction
  Connected stages are exposed through formed Fluid Ports and existing Tool
  resource access. Drain itself receives no external fluid capability. Existing
  resource-only conduit connectivity, endpoint adjacency, physical Buffer
  filters, and port filters govern accessibility. Each active server tick can
  evacuate staged contents into connected compatible physical Fluid Buffers.

  Normal container clicks on formed Vat Fluid Ports and Mixer fluid ports use
  NeoForge capability handling and FluidUtil transformation/stowing. Inputs
  preflight the complete offered transfer; outputs preflight the container's
  remaining capacity for the selected fluid. Failed/full/insufficient transfers
  leave fluid and containers intact and consume the click to prevent world
  placement. Vanilla/MobVats buckets, other standard containers, stacked
  containers, and NeoForge creative semantics use the same code path.
  Direct Fluid Buffer interactions retain Slice 11.1 behavior, including their
  standard partial capability-container policy.

  Unfiltered output chooses the lexicographically first eligible canonical fluid ID;
  eligibility includes container compatibility and full transfer capacity. Exact
  requested transfers aggregate that fluid across connected stage/bulk
  tanks. Ties retain deterministic physical position and service endpoint order.
  A port's exact filter is the intended fluid selection control. No GUI/cycling
  or conduit state is added. Unformed sneak sampling/clearing remains unchanged;
  formed sneak clicks retain locked-filter feedback.

Persistence and migration
  Endpoint saves preserve independent fluids and exact amounts. Reformation and
  controller assimilation retain the block entities and their stage contents;
  no controller assimilate/clear operation copies or deletes service state.
  Existing version-1 EndpointState portable data carries serviceStaging on
  producer drops and placement, excluding controller state and migration escrow.
  Formed port handlers resolve current connected tanks per operation, including
  following endpoint reload; they cannot retain replaced tank references.

  Vat legacy controller escrow remains unchanged and migrates to physical bulk
  capacity. Mixer legacy output prefers physical bulk capacity before legitimate
  bounded output staging; any remainder persists as migration escrow and retries.
  Water/Waste/Experience Mixer inputs gain no new invisible input reservoirs.

Diagnostics and limitations
  Status distinguishes Service: amount/1000 mB fluid-ID at endpoint from Bulk
  storage: amount/capacity mB. Output-blocked process status identifies service
  staging/bulk blockage. Existing bulk totals remain bulk views; service amounts
  are reported explicitly rather than presented as Fluid Buffer capacity.
  Generic port containers require a complete intended transfer; partial fluid
  availability is retained until sufficient fluid/capacity exists. Mixer recipe
  inputs still require their existing physical storage/input routes. Client
  visual/play acceptance remains manual. No Slice 11.3 void behavior is added.

Autonomous validation
  Slice112GameTests adds 17 focused tests, including actual Waste/milk production,
  actual Sword XP alongside full Waste, Blender Meat without bulk or Sword,
  independent Mixer recipe stages and formed slurry-port bucket extraction,
  filter/deterministic selection, complete bucket/generic capability transfers,
  failed partial transfers, stowing, disconnected stage isolation, aggregation,
  full/incompatible bulk evacuation and recovery, endpoint multi-fluid reload,
  reformation, actual controller assimilation, portable producer drop/placement,
  and bulk-first Mixer legacy migration with retained overflow and reload retry.
  Older capacity tests now fill service as well as physical bulk storage before
  asserting blockage; physical tank-count assertions allow service endpoints.

  Required commands: gradlew.bat build; gradlew.bat runGameTestServer;
  git diff --check. Final suite: 285 required tests. No client task is run.

Manual client acceptance
  1. Produce Waste with no Fluid Buffer; retrieve up to one bucket.
  2. Retain 1000 mB Waste and 1000 mB Experience at the same Drain.
  3. Bucket each desired fluid through separately filtered Fluid Outputs.
  4. Add a compatible Fluid Buffer; observe evacuation and continued production.
  5. Produce, retain, and retrieve one bucket of milk without a Fluid Buffer.
  6. Produce, retain, and retrieve one bucket of Meat without a Fluid Buffer.
  7. Retrieve a bucket of each Mixer slurry without bulk output storage.
  8. Confirm normal formed-port container transfer and locked sneak filters.
  9. Save/reload partial and full stages; verify exact amounts and ownership.

No client launch, publication, release, or deployment is part of this slice.
