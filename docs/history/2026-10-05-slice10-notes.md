MobVats Slice 10 - Multiple independent simulacra
================================================

Scope: Minecraft 1.21.1 / NeoForge / external ZeroCore2.
No publication, release, or client task was performed. Visual acceptance remains manual.
Clearance observations do not modify productivity in this slice.

1. Multi-assembly discovery
--------------------------
Formation requires one Controller and at least one encoded Head. Every Head resolves
its own persisted SimulacrumGeometry. Discovery validates the complete occupied-cell
ownership map before validating Head/Flesh substrate, then constructs all MobAssemblies.
Assemblies are sorted by Head X, then Y, then Z. Flesh adjacency never discovers or
expands a specimen. Touching, one-gap and two-gap layouts are legal. Overlap, missing
substrate, stray Flesh, invalid definitions, or ambiguous services reject formation
with coordinates in the diagnostics; invalid specimens are not silently skipped.

2. Harness and Drain ownership
------------------------------
Each specimen resolves its complete footprint-corner Harness plane independently.
One Harness may belong to only one specimen; extra unassociated Harnesses are invalid.

Each Drain selects one eligible specimen. Eligibility retains the existing below-body
vertical range and horizontal offset range. Selection minimizes horizontal Manhattan
distance to the occupied footprint, then vertical distance below its bottom. Equal
distance is ambiguous and rejected. Each specimen must receive exactly one Drain;
unassociated or extra Drains reject formation. Drain assignment is computed from all
Heads before individual association, avoiding the old issue where a nearby specimen's
Drain would be counted as a second Drain. Drains remain waste endpoints without a
Culture fluid capability.

3. Runtime state
----------------
SpecimenProcessState remains authoritative and keyed by Head BlockPos. Each entry owns
LifeStage, growth, secondary timers, generic/pending process state, and last committed
feed source. Captured identity/state and geometry remain on the individual Head.
Shared fluid buffers, XP, kill output, support pools, topology, and metrics remain on
one controller.

A persisted Head specimen UUID binds each process entry to the actual Head at that
position. Removing and immediately replacing a Head cannot transfer old progress or
stage to the replacement. Existing saves without UUID bindings adopt their current
Head once, preserving legacy state. Changing the encoded entity identity renews the
Head UUID. Reformation of the same persisted Head preserves its UUID and state.

4. Scheduling and fairness
--------------------------
Contexts compile once per topology/profile revision. A flat ordered Head list and
position lookup cache serve ordinary ticks. Stable X/Y/Z order is rotated by one
starting Head after each 10-tick process cadence. The next Head and cadence offset
are persisted. A removed cursor target falls forward to the next position, wrapping
at the end. Transaction evaluation and shared-resource commits follow this order.
Culture tick allocation uses the same rotating start. No priority scheduler or
species grouping was introduced.

Topology changes caused by acquisition, tool transformation, or LifeStage transitions
refresh subsequent contexts by Head position. Earlier specimens' process diagnostics
survive these recompilations; removed definitions and Heads lose stale diagnostics.

5. Shared resource accounting
-----------------------------
Configured buffer definitions are unioned across all resolved profiles before one
controller buffer configuration. This prevents the last profile from removing an
earlier profile's active buffers. Shared IDs remain one tank. Conflicting definitions
for the same ID retain the stable first Head's definition and expose a diagnostic;
committed fluid contents remain preserved. Configuration authors should use matching
definitions for shared IDs or distinct IDs for distinct resources.

Item/fluid/XP/output/lifecycle changes continue to commit through the existing atomic
transaction engine. Capacity failure retains each specimen's pending work. Direct
Item Input feed remains restricted to compiled per-Head physical contacts. Conduits
expand selected actors' endpoints; no global Item Input feeding was introduced.

6. Actor assignments and tool loading
------------------------------------
Priority remains local to Head + use. Blender 200 beats Sword 100 only for that Head's
HARVEST use. Successful claims bind each actor to at most one Head across its uses.
Equal-priority candidates sort by actor position, then Head position, then use.
Displaced actors may select another eligible Head; blocked routes are filtered before
selection. An empty Tool Port's loading route selects one Head deterministically.

Acquisition runs in the specimen's cached context and uses its own stage, feed,
definition, selected processes, and local/conduit endpoints. Shared scarce supply is
allocated in rotating specimen order. A juvenile or otherwise ineligible specimen
does not load a bucket or Sword just because another specimen can use it.

7. Kill item buffer
-------------------
The controller-wide kill item buffer is unchanged. While nonempty it blocks every
Sword/item-kill replacement in that Vat. The first eligible Sword commits one batch;
later specimens see the resulting backlog immediately. Draining all committed items
through generic outputs permits subsequent Sword work. Blender MEAT commits continue
independently when their shared fluid buffer has capacity.

8. Culture and Feeding Slurry
----------------------------
Culture preserves paid 4x behavior. The old profile-wide multiplier cache is removed.
An eligible specimen with accelerated timer work spends one paid support-budget tick;
another specimen must spend another tick. Ready, inactive, paused or unaccelerated
work does not consume acceleration credit. A default payment of 10 mB purchases ten
specimen work ticks, not ten Vat-wide ticks. Profiles with different Culture prices
use separate shared credit pools keyed by configured cost, so a cheap profile cannot
pay for an expensive profile's work. Credit pools survive reload and assimilation.

Each committed replacement consumes its own configured Feeding Slurry dose, atomically
with its output and lifecycle change. Scarce doses rotate among eligible specimens.
Specimens without harvest actors do not consume feed. No clearance multiplier exists.

9. Rendering and status
-----------------------
VatRenderDescriptor resolves the requested Head's assembly rather than the first
assembly. Each Head renders its own captured identity/state, stage, Harness straps,
and assigned mechanisms. Tool links are transported once to the assigned Head;
unassigned idle Tool Ports use the first Head as a single render anchor. Conduits also
render once from that anchor. Vat-level bounds and FULL/REDUCED/MINIMAL/CULLED detail
selection are shared through a camera/bounds/settings cache. No real world entities,
entity ticking, AI, or pathfinding were added. Client visual inspection was not run.

Controller pages expose total/validated/unvalidated Head counts, actor/endpoint counts,
shared buffers, next scheduled Head, and separate identity/position specimen sections.
Each section exposes stage/progress, Harness positions, Drain position, harvest actor,
feed source, process results/waiting reasons, work multiplier, and clearance observations.
Aggregate milk/item/XP/MEAT/Waste metrics remain controller-owned. No GUI redesign or
persistent per-specimen throughput history was added.

10. Reload, removal, reformation and assimilation
-------------------------------------------------
All specimen states, pending data, owner UUIDs, the next-Head cursor, cadence offset,
shared buffers, and support pools serialize. Topology/context/presentation caches are
derived again after restoration. Successful assembly prunes removed Head states;
new Heads initialize independently. Head UUID binding additionally handles immediate
same-position replacement before an intervening successful reformation.

Assimilation keeps the destination state on same-position collisions and imports
non-colliding states with their UUID bindings. An empty destination adopts the source
scheduling cursor/offset; otherwise destination scheduling authority remains intact.
Existing additive XP, kill-buffer, fluid-overflow preservation and metric conventions
remain. Credit pools merge by matching cost. No committed buffer is silently discarded.

11. Clearance preparation
-------------------------
Each topology rebuild caches per-Head SpecimenClearance against all validated assemblies.
Neighbor body intersections, occupied comfort-shell cells, and service geometry remain
observations. Touching specimens see each other's body intrusion. One-gap specimens
share comfort-shell cells; two gaps permit independent shells. Status reads the cache,
avoiding repeated world clearance scans at each process/status cadence. Formation and
throughput do not depend on these observations.

13. Remaining assumptions and limits
------------------------------------
No runtime discovery, state, scheduling, or render-descriptor path assumes one specimen.
The first Head is deliberately used only for once-per-Vat conduit and unassigned-idle
mechanism rendering. Single-specimen construction helpers remain in regression tests.
Existing Cow-named compatibility snapshot/network fields and legacy milk/feed metric
names remain adapters; they do not group runtime processing by species. Existing
one-slot Item Ports and shared dynamic fluid/XP/kill buffers are retained by design.
The four existing menu tabs retain their 32,767-character transport cap per page;
very large Vats or verbose custom profiles can truncate detailed status text. Overview
counts remain available. The decorative menu item still samples one selected Tool;
per-specimen assignments are listed in the text diagnostics. Full GUI pagination is
outside this slice's requested scope.

The Vat must validate as a whole; incomplete or ambiguous specimens prevent formation.
There is no automatic packing, shared Harness/Drain ownership, actor multi-service,
per-specimen tank, or clearance-based throughput adjustment. Same-ID conflicting
buffer definitions require configuration correction despite preserved contents.
