MobVats Slice 12 - Configurable Mixer and compound-fluid foundation

IMPLEMENTED CONTRACT

The Mixer uses server JSON definitions under config/mobvats/mixer/. Startup copies
bundled data/mobvats/mixer_defaults.json to _defaults.json only when absent. Existing
user files are never overwritten. _defaults.json loads first, then other .json files
in filename order. Later files replace recipes with the same ID and names for the
same family/formula. Execution order is sorted recipe ID. /mobvats reload_mixer
reloads definitions on the server thread and synchronizes formula names to clients.
Invalid files produce diagnostics and contribute no partial definitions. Other valid
files remain active. Duplicate fields, unknown fields/registry IDs, missing fields,
nonpositive/fractional/overflowing amounts and invalid ingredient forms fail cleanly.
Tag membership remains live; tags are never expanded into composition members.

A file has an optional recipes object keyed by recipe ID and an optional names array.
Each recipe has:
  items: [{selector, amount}]          optional, item units
  fluids: [{selector, amount}]         optional, millibuckets
  output: registered source fluid ID
  output_amount: positive millibuckets
  batch_ticks: positive active ticks (cadence granularity is 10 ticks)
  composition: [{kind, selector, amount}] optional explicit output formula

At least one input is required. Selectors accept an exact ID, #tag, or native
NeoForge ingredient JSON (object/array), including neoforge:components and custom
registered ingredient types. Ingredient codecs receive registry-aware operations.
Registry IDs remain validated by the native ingredient codecs. The original JSON
selector identity is retained, with object keys sorted, separately from its matching
predicate. Array order is preserved as authored. Matching supports mixed tag members
and overlapping exact/tag ingredients without consuming resources twice.

Without composition, compound outputs derive their formula from the configured
inputs. Ordinary outputs receive no composition. Explicit composition is allowed
only for compound outputs, must be nonempty, and must describe underlying resources
rather than reference an exact compound family. Optional explicit composition also
allows an administrator to author a deliberate recovery/reprocessing recipe for
unknown legacy material or collected spills. No unrequested recovery formula is
injected into Java or assigned to unknown old contents.

FLUID FAMILIES AND SAVE COMPATIBILITY

Semantic culture fluid keeps mobvats:culture_slurry (and its existing flowing fluid,
bucket and block IDs). Semantic feed fluid keeps mobvats:feeding_slurry and its IDs.
The new generic process family is mobvats:component_fluid, with a flowing variant,
bucket and liquid block. These are real registered world-placeable fluids. Culture,
feed and component fluids use turquoise, green and purple client tints respectively.
No dynamically registered per-formula fluid exists. Client visual acceptance remains
user-controlled; no client tasks or manual UI testing were run for this slice.

Meat, waste and experience remain ordinary stable registered fluids. Adding bucket
metadata support does not attach a composition or change their semantic identity.

Old controller tank0 through tank4 NBT and old XP fields load into migration escrow.
Escrow retries transfer to compatible physical storage, retaining overflow and all
components across save/reload. New state persists a generic escrow list; physical
fluid contents are never saved as another authoritative controller copy. Old tank
keys are compatibility views of escrow, not a second source of resources. Existing
slurry without composition stays intact and usable by existing Vat/Feed compatibility
logic. It is distinct from a newly authored compound formula. Derived processing of
an unknown compound input blocks before consumption; explicit configured reprocessing
is available if the administrator wants to assign a new formula.

COMPOSITION AND FORMULA BASIS

mobvats:composition is one immutable persistent/network-synchronized data component
usable on FluidStack. Each entry has ITEM or FLUID kind, configured selector identity,
and a positive 32-bit quantity. Entries sort by kind and selector; identical selectors
combine with checked integer addition. Exact selectors and tags remain distinct.
Quantities are not reduced to ratios. Tags are not expanded. Up to 4096 canonical
entries and the normal network string length are supported.

FluidStack.amount is ordinary volume. Copying, splitting, draining and merging change
only that volume; the component formula is unchanged. Identity is fluid plus all data
components, not just the composition component and never just the registry Fluid.

For a compound fluid input, derived output adds ONE complete stored formula per
distinct full compound identity consumed by that configured input. The consumed mB
quantity does not scale that formula. Splitting identical material across physical
buffers does not duplicate it. Separate configured inputs each contribute their own
formula. If one input consumes different compound identities, each distinct formula
contributes once. Combining entries then produces one flat canonical formula. No
concentration calculations, ratio normalization, fractional units or rounding occur.
A selector that consumes both ordinary and compound material in the same input is
blocked for derived output; define separate inputs or an explicit composition.

STORAGE, TRANSPORT, FILTERS AND CONTAINERS

Recipe execution plans generic connected physical tanks and item slots, preflights
complete input allocation and output capacity, and commits internal final tank states.
Outputs prefer compatible physical buffers, then the producing endpoint's existing
bounded service staging. Unlike compositions cannot merge. Service staging remains
one bounded bucket per output family; a different formula blocks while that family's
service tank is occupied. This preserves Slice 11.2/11.3 staging behavior. No live
controller bulk tanks are introduced. Unbound MixerState instances serve isolated
process tests/client snapshots; live server controllers bind immediately.

Mixer Item Inputs accept ingredients referenced by loaded recipes, including nonplants.
Fluid Inputs accept configured ordinary or compound resources. Output recipes choose
any registered fluid. Existing amount(index) methods and legacy metric aliases remain
compatibility presentation helpers and do not determine recipe execution/storage.

ResourceFluidTank views copy a real stored stack and aggregate only identical full
identities. All drain requests use copied stored stacks. Conduits and Fluid Ports keep
drain/fill stack components. A sampled component-bearing filter uses an encoded exact
FluidStack identity with amount fixed to 1; it persists as an '=...JSON' selector.
Ordinary component-free samples keep their existing plain-ID format, and configured
plain IDs/tags continue to select families. Tank contents still enforce full identity.

All MobVats product buckets preserve the complete FluidStack in immutable container
metadata, including components unrelated to composition. Native standard wrappers
would reconstruct only the Fluid, so MobVats supplies preserving fluid types, bucket
items and capability handlers. Empty bucket transformations receive a full-stack
snapshot. Container extraction inspects a transformed copy before spending source
fluid. Third-party/vanilla containers that discard components are rejected by MobVats
interactions instead of silently destroying metadata. Generic capable containers may
participate normally when they preserve the full identity.

WORLD SPILL BOUNDARY

Minecraft FluidState/LiquidBlock stores a registered fluid and ordinary state properties;
it has no FluidStack component map per source/flowing cell. Exact per-cell composition
would require an additional persisted and synchronized world data model, together with
flow, displacement and pickup rules. This slice deliberately chooses family-level
spills using standard NeoForge flowing fluids and LiquidBlocks.

Buckets, Push Pumps and Fill Valves crossing into world fluid state preserve FAMILY,
not composition or other arbitrary stack components. Bucket tooltips state that loss.
Picking up a source, Pull Pump collection and Drain Valve collection return the same
family with unknown composition. No formula is silently recreated. Contained transport
preserves all components until the explicit world placement boundary. World family
placement and pickup are exercised autonomously; no cell-specific composition storage
is claimed. Original Slice 11.3 medium eligibility and boundary-device logic remain.

NAMES AND FUTURE SLICES

The names array maps family + exact canonical composition to display_name or
translation_key. Names are synchronized to negotiated clients on login and reload.
Unknown formulas use the generic family name and composition tooltip; legacy/spill
buckets explicitly say their composition is unknown. Names are never written into
fluid identity. See ../examples/MIXER_RECIPES.example.json for staged recipes and a named formula.

No happiness, culture productivity/frequency effects, consumption, dirtying, cleaning,
quality gates or new Feed Port behavior are introduced. Later interpreters can use
configured selectors and the persistent component without new fluid registry types.
